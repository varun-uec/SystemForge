How Breakscale works

Breakscale is a discrete-event simulator wearing a diagram editor. You build a topology, drag a load slider, and a real event loop runs requests through queues, servers and failure modes fast enough to redraw ten times a second. Nothing here is a static app with a backend — the whole thing, engine included, runs in the tab that's open right now.

The loop that runs it

Every request on the canvas is a real object moving through a discrete-event simulation living in src/sim — no React, no DOM, no I/O. It owns a min-heap of future events (arrivals, service completions, timeouts) and a seeded PRNG, and nothing else. You could delete every component file in the repo and still run it from a script.

Where the numbers come from

The project's one hard rule, stated in its own contributor guide: a number is measured or it doesn't ship. Three mechanics make that true rather than aspirational.

Percentiles are read off a ring buffer

Every node keeps a fixed-size ring buffer of its own completed request latencies, each timestamped. Reading p50/p95/p99 means walking that buffer newest-first, stopping at a trailing time window, sorting what's left, and interpolating — the same thing a real APM tool does, not a multiplier applied to a mean. Because the UI polls this at 10Hz but the underlying samples only change when a request actually completes, the result is memoized per (time, sample count) so an unchanged window is never re-sorted for nothing.

Service time has real variance

A component's config gives a mean service time and a coefficient of variation, sampled from a gamma distribution (shape k = 1/cv²) via a Marsaglia–Tsang sampler. cv = 0 is deterministic, cv = 1 is exponential, and anything above that is heavy-tailed — which is what makes p99 diverge from p50 at all. A mean-only model would give every percentile the same number.

The same seed replays the same system

All of it — arrivals, service times, which replica an autoscaler spins up — is drawn from a single seeded mulberry32 generator. Same topology, same seed, same traffic pattern: byte-identical snapshots, every time. That determinism is what a worked example's "note" can rely on — the failure it describes is guaranteed to be the failure a student sees.

03

Four doors, one lock

Breakscale has no server, so nothing is ever uploaded — but that doesn't mean nothing is untrusted. Four different features hand the app JSON that came from somewhere else, and every one of them is treated as hostile until proven otherwise.

The share link, specifically

A design travels entirely in the URL fragment — everything after # — because a browser never sends that part to a server, so a link really is a complete, self-contained document. The payload is a version prefix (d1.) followed by base64url text; where the browser supports it, the JSON is deflated first, since a twenty-node example can be several kilobytes. The decoder caps output bytes mid-stream, not just input — the standard defence against a small link inflating into hundreds of megabytes before anyone notices.

What lives where

Everything persists to localStorage, scoped to your browser on this one machine. Five keys, five different lifetimes:

KeyWhat it holdsWritten
breakscale.session.v1The design you left open — restores on reload, autosaved, never announced.Continuously, debounced
breakscale.designs.v1Named saves — up to 20; the oldest is evicted, and you're told when it is.On "Save"
breakscale.preferences.v1Theme, vendor mode (AWS / GCP / Azure / generic), glossary tooltips.On change
breakscale.layout.v1Panel sizes — the inspector rail, the charts strip, the minimap toggle.On resize
breakscale.sizes.v1Which vendor instance size each node is priced at (db.r6g.large, and so on).On pick

A backup is the door out: one JSON file carrying all five keys' raw values, for moving to a new machine or surviving a cleared cache. It replaces rather than merges on restore — there's no principled answer to which of two designs named "draft" should win, so the app doesn't pretend to have one.

05

33 components, one registry

Every component kind — load balancer, cache, sharded store, circuit breaker, websocket gateway — is a plain string literal plus a behaviour object resolved once when the topology is built. The event loop never branches on kind === 'cache' anywhere; it holds a reference to that node's behaviour and calls through it, so adding a kind never touches the hot path. The bar for a new one, enforced by the project's own contributor guide:

  1. Declare the kind in NodeKind.
  2. Config fields, each documented with its meaning and units.
  3. A behaviour object in the matching behaviour-*.ts file — control, data, edge, messaging, resilience or store.
  4. Default config and a palette label.
  5. A readout in readoutFor — never a field that's structurally always zero for that kind.
  6. A glossary entry, written for a reader who hasn't taken a queueing theory course.
  7. A test proving it behaves differently from every existing kind — a kind that's just another kind with different defaults doesn't get added.
